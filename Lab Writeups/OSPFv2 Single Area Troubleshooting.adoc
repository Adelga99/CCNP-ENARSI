## R1 <> R6 Adjacency

I noticed that the third octet in the IP addressing for this lab contains the router numbers. So 172.16.12.0 is for R1 and R2, and the R1 <> R6 connection _should_ be 172.16.61.0. +
If you look back at the previous seciton, R1's configuration had the incorrect network and IP address configured on this connection, and neighboring routers must share a common subnet in order to form a full adjacency. +

A quick few changes on R1 brings up the adjacency: +

image::Images/OSPFv2%20Single%20Area/R1_R6_ADJACENCY.png[]

{blank} +
And with that, R1 now has full adjacencies with both of its neighbors.

## R3 <> R4 Adjacency
This connection did _not_ come up immediately, so I gathered information from R3. +
All interfaces were up, the OSPF configuration was correct, and the network type was set to broadcast (the default on ethernet interfaces). +

I turned my attention to R4, and noticed that the link to R3 had been configured as point-to-multipoint. Unfortunately, this is not a DMVPN lab, so I changed the network type back to broadcast and the adjacency came up: +

## R5 <> R6 Adjacency
Initially, R5 did not seem to be configured incorrectly. Timers were the default broadcast timers, the OSPF configuration on the device seemed correct, and the interface was online. +
Without looking back at R6, I ran _"debug ip ospf packet"_ on R5 to see if there was anything in the packet that would stand out. +
Sure enough, the packets received inbound from R6 had _auth:2 keyid:1_ in them, meaning R6 had MD5 authentication configured on the interface.

image::Images/OSPFv2%20Single%20Area/R5_DEBUG_AUTHENTICATION.png[]

{blank} +
Logging into R6 and checking the running configuration showed the config lines _"ip ospf message-digest-key 1 mdf cisco123"_ (designating a key), and _"ip ospf authentication message-digest"_ (telling OSPF which algorithm to use). +
I added those same lines to R5, and our last adjacency was formed.
